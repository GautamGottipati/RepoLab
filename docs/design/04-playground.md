# Spark Playground — `/r/{jobId}/playground`

## Purpose

Run the repository's actual job and show what really happened. Five panels, in
the order the spec names them: input data, pipeline, configuration, execution,
metrics.

## Reads and writes

- `GET /runs/dataset?rows=` — the deterministic dataset spec and its first rows.
- `POST /runs` `{repo_url, shuffle_partitions, rows}` → `202 {job_id}`.
- `GET /jobs/{job_id}/events` (SSE) — execution progress.
- `GET /jobs/{job_id}/run` — the measurements, once there are any.
- `GET /runs?repo_url=` — previous runs, for comparison.

## Panels

**Input data** — rows, distinct keys, the skewed key and its share, the dataset
`sha256`, and a sample of the first rows. The sample is cut from the real
generated bytes, so the hash shown is the hash the run will record.

**Pipeline** — the stages, in order:

```
read CSV  →  repository's transform_data()  →  repartition by dept
          →  groupBy + aggregate  →  write
```

The repository's own step is marked as the repository's. The three RepoLab adds
are marked **added by RepoLab**, with the reason, from the run's `added_steps`.
The repository's job performs no shuffle at all; without the addition there
would be nothing to measure. Saying so is not a footnote, it is the honest
framing of every number on the screen.

**Configuration** — `spark.sql.shuffle.partitions` as an editable control (the
subject of the demo question), and the rest as read-only facts: master, driver
memory, adaptive execution disabled, the image. Adaptive is disabled on purpose
— it would coalesce partitions and hide the distribution this run exists to
measure — and the panel says that.

**Execution** — the run button, the elapsed time, and the live event feed for
this run: environment, clone, dataset, spark-submit, event log collected.

**Metrics** — after the run, split exactly as the backend labels them:

- *Structural* (repeats exactly): stages, tasks, shuffle read/write, spill,
  partitions, **empty partitions**, heaviest partition, skew ratio.
- *Timing* (varies between runs): total runtime, slowest task, median task.

Empty partitions get a bar: 193 of 200 is the finding the whole demo turns on,
and a number in a table does not land the way a bar does.

Below the metrics: the preserved event log's path, size and `sha256`, and the
measurement source of every figure.

## States

- **Environment unavailable** — if investigation reported Docker missing, the
  run button is disabled and says why. The rest of the screen still renders.
- **Running** — progress from the event stream; the metrics panel shows a
  skeleton.
- **Failed** — the failure message from the stream, and the event log if one was
  produced.
- **Previous runs** — listed with their partition count and runtime, so two runs
  can be compared before any experiment is proposed.

## Must never show

- A metric with no event-log field behind it.
- A timing presented as reproducible.
- The dataset sample as anything other than the real generated bytes.
